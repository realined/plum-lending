# Build journal

This journal records architectural checkpoints and verified results. Code being present is not proof of completion. Live acceptance is mandatory and remains pending until explicitly authorized real-account testing passes.

## Phase 1 — Domain foundation

**Goal.** Convert a natural-language request into reviewed constraints and determine contact/thread eligibility without AI decisions.

**Decisions.** Strict TypeScript; Zod for intent/spec validation; frozen as-of UTC instant; calendar-month arithmetic; exact case-insensitive identities; direct contact-to-deal association scope; current Closed Won stage excludes across all time. Exact reference header is `Email Body`, populated with complete thread text.

**Implementation.** `src/domain/segment.ts`, `models.ts`, `identity.ts`, `executor.ts`, and `csv.ts`; synthetic positive/negative dataset in `src/providers/demo.ts`; provider-independent contracts in `src/providers/contracts.ts`.

**Data flow.** Reviewed SegmentSpec + CRM snapshot + full threads → deterministic sender/recipient/date/deal checks → one row per contact/thread → quoted, formula-safe CSV with normalized JSON.

**Validation.** 60 domain tests passed. Tests exposed and prompted fixes for invalid date refinement throwing, fractional-second timestamp comparison/order, and repeated message IDs in export evidence. No live credentials or correspondence used.

**Alternatives.** SQL generated by an LLM or autonomous provider tools were rejected because validation, explainability, and authorization are weaker. Concatenating an entire contact history into one cell was rejected in favor of contact/thread rows. Fuzzy identity matching was rejected because false joins could expose or misattribute correspondence.

**Assumptions and remaining work.** Current stage represents Closed Won; historical reopened wins are outside this slice. Live role property and aliases must be confirmed during setup. MIME/provider contract tests and end-to-end validation remain separate gates.

**Interview talking points.** Runtime versus TypeScript validation; AI interpretation versus deterministic execution; inclusive/exclusive time boundaries; identity precision; thread-level evidence and exclusion reasons.

## Phase 2 — Persistence, integrations, and jobs (verification in progress)

**Goal.** Retrieve provider data safely and make long-running exports durable.

**Decisions.** PostgreSQL schema with Drizzle; PGlite for a one-process credential-free demo; ordinary PostgreSQL plus a dedicated worker for live mode. Atomic claims, expiring leases, heartbeats, and owner fencing. AES-256-GCM tokens. Google authorization code + PKCE + expiring state; Gmail read-only scope. HubSpot private-app token validated server-side.

**Implementation.** `src/db/schema.ts`, migration SQL, `src/server/database.ts`, `repository.ts`, `worker.ts`, `connections.ts`, `oauth.ts`, `auth.ts`, and `src/providers/{gmail,hubspot,http}.ts`. Provider responses are translated into canonical entities. Association uncertainty fails closed.

**Alternatives.** Redis/BullMQ would add a second service for a workload adequately handled by a PostgreSQL queue. Request-local background promises were rejected because they do not survive process termination. Provider SDKs were avoided for a small read-only surface with explicit Zod response validation.

**Validation.** Domain tests pass; provider, MIME, storage/recovery, API, and browser tests are pending. Type checking found a driver generic cast mismatch, corrected at the database boundary; full checks will be rerun.

**Assumptions and remaining work.** Single workspace and one Gmail identity; configured lender aliases. Gmail history adapter exists but continuous materialized sync is not yet scheduled. Real Gmail, HubSpot, and OpenAI have not been connected. Live testing is mandatory, with explicit user authorization before connection or processing.

**Security.** Tokens server-side, encrypted at rest; sessions signed; mutation origins checked; no message or token logging. Local data deletion fences jobs by removing parent records. Deployment hardening and retention remain documented production work.

**Interview talking points.** At-least-once processing; idempotency versus exactly-once claims; lease fencing; fail-closed CRM eligibility; provider normalization boundaries.

## Phase 3 — Admin workflow (implementation in progress)

**Goal.** Make interpretation and evidence reviewable before and after execution.

**Decisions.** Server stores the interpretation; the browser runs its ID rather than submitting an arbitrary spec. Poll durable state; explicit partial/empty/error states; paged preview and streamed CSV. Synthetic scenarios visibly labeled.

**Implementation.** App Router API and `src/components/workspace.tsx`, `results.tsx`, responsive CSS. Connection, interpretation, job, history, preview, full-thread drawer, and download views.

**Validation.** Pending type/lint/build and Playwright flows and visual inspection.

**Assumptions.** Single administrator; shared-password local POC authentication. No public deployment. No live data processed.

**Interview talking points.** Human review at the interpretation boundary; immutable request-time semantics; partial results versus completeness; evidence-first UI; sensitive-content rendering as text.
